# Orquesta セッション世代交代 設計

作成日: 2026-07-31

対象: Orquesta V4 Fast
状態: V4 Fast実装済み。実測調整前

## 結論

長期稼働する各エージェントは、役割と機械IDを維持したまま、Codexセッションだけを世代交代する。

交代の既定値は、ユーザーの長期運用時の体感とOrquestaの再起動費用をもとに、次の三段階とする。

| 圧縮回数 | 状態 | 動作 |
| --- | --- | --- |
| 12 | `rotation_preparing` | 正式状態と証拠の不足を検査し、引き継ぎ可能な状態を準備する。まだ交代しない |
| 15 | `rotation_pending` | 次の安全な区切りで交代する候補になる。後継セッションの起動準備を許可する |
| 20 | `rotation_required` | 新しい仕事を受け付けない。現在の最小作業単位を完了してから必ず交代する |

20回に到達しても、ツール実行、ファイル書き込み、状態遷移、ユーザー承認待ちの途中ではセッションを切らない。`required`は即時終了ではなく、新規受付を停止して安全地点へ移動するという意味である。

この回数は固定ロジックではなく、プロジェクト設定で変更可能な既定値として持つ。値を変更しても状態遷移の意味は変えない。

## 交代単位

- `agent_id`と役割は維持する
- `session_generation`を1増やす
- 新しい`thread_id`をCodex App Serverの`thread/start`で作る
- `thread/fork`は古い履歴を複製するため使用しない
- 圧縮回数はセッション世代ごとに0へ戻す
- 統括者と各専門家は、それぞれ独立して交代する

## Desktop上の論理会話

Codexのセッションと、ユーザーから見えるOrquestaの人物を分離する。

Desktopの会話先は`thread_id`ではなく、安定した`agent_id`を持つ一つの論理会話として表示する。統括者が世代交代しても、通常画面に「統括者A」「統括者B」を増やさない。組織図と会話一覧には、引き続き一人の「Orquesta 統括」だけを表示する。

各世代の会話本文を物理的に一つのログへコピーしない。`sessions.json`に同じ`agent_id`の世代履歴を保持し、Desktopが複数のCodex threadを時系列に連結して表示する。これを論理会話projectionとする。

- 会話channelの主キー: `project_id + agent_id`
- 実際のメッセージ出典: `thread_id + session_generation + message_id`
- 通常表示: 全世代を一続きの会話として表示
- 詳細表示: メッセージごとの世代とCodex threadを確認可能
- 送信先: `active`で最も新しい世代だけ
- 古い世代: 読み取り専用
- ページング: 新しい世代から読み、必要な場合だけ前世代を遅延取得

世代境界には、通常の発言とは別の小さなシステム表示を挿入する。

> セッションの健全性を保つため、Orquesta 統括の実行セッションを世代2へ引き継ぎました。

境界表示は会話を分断するタブではなく、同じ人物が内部セッションだけを交代したことを説明する区切りとする。

メッセージIDは`thread_id`を名前空間に含め、別世代で同じIDが使われても重複しないようにする。表示名や役職名が同じという理由だけでは結合せず、同じ`agent_id`の世代だけを結合する。

旧セッションの本文を読めなくなった場合は、黙って欠落させない。世代境界に取得不能を表示し、保存済みの正式状態、暗黙知差分、引き継ぎmanifestは引き続き参照できるようにする。

現在のDesktopは、一つの`agent_id`から一つの現役`thread_id`を解決し、そのthreadだけをApp Serverから読む実装である。そのため、世代交代の実装では次を同時に変更する。

1. `sessions.json`で旧世代を上書きせず履歴として残す
2. 実行時の送信先解決は、検証済みの最新`active`世代を一意に選ぶ
3. 会話読込は同じ`agent_id`の全世代を対象にする
4. 組織図はsession行ではなくagent行を基準にし、人物を増殖させない
5. 旧世代のアーカイブ後も読めるかをApp Server実環境で確認してから、自動アーカイブを有効にする

## 状態遷移

```text
active
  -> rotation_preparing
  -> rotation_pending
  -> draining
  -> checkpointed
  -> successor_warming
  -> successor_verified
  -> active (next generation)

旧セッション: successor_verified後にsuperseded
失敗時: 旧セッションがactiveへ戻り、所有権を維持
```

## 引き継ぐ情報

会話全文や巨大な要約は渡さない。次の五つを参照する小さなmanifestを作る。

1. 変更されない役割契約
2. 正式状態にある現在のタスク、段階、次の操作、保留事項
3. 直近会話から切り出した、上限付きの未要約な暗黙知候補
4. ファイル、差分、テスト、レポートなどの証拠
5. Context V2が選んだ必要資料

V4 Fastでは、劣化した旧担当へ追加の要約ターンを強制しない。要約による二重劣化を避けるため、直近会話を上限32,000文字、1発言4,000文字で未要約のままmanifestへ含める。正式状態は会話より常に優先する。V5では世代横断の暗黙知検索へ置き換える。

暗黙知候補には、少なくとも次が残るようにする。

- 判断とその理由
- 却下した案と却下理由
- ユーザーの好み、ニュアンス、強い禁止事項
- まだ確定していない推測
- 次の担当が最初に確認すべきこと

正式な事実は`.orquesta/state`から復元し、暗黙知差分へ重複して書かない。

## 安全な交代手順

1. 圧縮イベントを数え、12、15、20の状態を記録する
2. 交代対象は新規タスク受付を停止する
3. 実行中の最小作業単位を完了し、副作用を確定させる
4. 正式状態のrevisionと証拠参照を固定する
5. 正式状態と上限付き会話末尾からhandoff manifestを保存する
6. 新しいCodexセッションを`thread/start`で起動する
7. 新担当がmanifestと参照先だけを読み、状態を再構築する
8. 新担当がrevision、タスク、Git差分、必要な最小テストを照合する
9. 構造化receiptが合格した場合だけ、所有権を新しい世代へ原子的に切り替える
10. 旧セッションを`superseded`にする

後継の検証に失敗した場合、旧セッションが所有権を維持する。旧世代と新世代を同時に書き込み可能にしない。

## 検証receipt

新担当は次を返す。

- `agent_id`
- `expected_generation`
- `observed_generation`
- `state_revision`
- `active_task_ids`
- `next_action`
- `blockers`
- `evidence_checked`
- `disagreements`
- `ready_to_assume_ownership`

文章で「理解しました」と返すだけでは合格にしない。

## 実装境界

V4 Fastでは、圧縮回数の計測、状態遷移、manifest、後継検証、所有権切替までを実装する。

暗黙知を長期検索したり、複数世代から学習したりする記憶システムはV5へ分離する。V4 Fastの暗黙知差分は一世代間の引き継ぎだけを目的とする。

Codexの圧縮イベントを取得できる環境では`PostCompact`を計測元にする。Desktopが閉じていても交代要求を失わないよう、回数と状態はDesktopのメモリではなく`.orquesta/state`へ保存する。

旧統括セッションは交代直後に自動アーカイブしない。子セッションへの影響を確認できるまで、所有権を外した`superseded`状態で残す。

## 調整方針

12、15、20はV4 Fastの既定値として採用する。ただし、最適値が外部資料で証明されているわけではないため、実運用では次を記録する。

- 各世代の圧縮回数
- 交代準備から所有権切替までの時間とtoken
- 引き継ぎ後の修正、再読込、誤解の件数
- 交代しなかった場合の文脈劣化兆候

値はこの実測を見て変更する。個別ベンチマークの点数だけを上げるためには調整しない。

## 実装結果

- `PostCompact`を数えるプロジェクトローカルhookを初回セットアップとDesktopのproject openで配備する
- Desktopが閉じていても回数と交代要求は`.orquesta/state/session-rotation.json`に残る
- Desktop Coreは安全地点でfresh threadを作り、manifest、構造化receipt、所有権cutoverを順に処理する
- receipt不一致時は旧世代が所有権を保持し、候補世代だけを`failed`にする
- 送信先解決はrotation registryを優先し、projection更新途中でも二重所有を起こさない
- Desktopの履歴は同じ`agent_id`の世代を遅延取得で連結し、世代境界だけ小さく表示する
- 旧threadは自動archiveせず、`superseded`の読み取り専用履歴として残す

Codexのproject hookは信頼確認の対象になる。新規配備後、そのprojectでCodexがhook設定を読み直すまでは圧縮イベントを取得できない。これはCodex側の安全境界なので、Orquestaが無断で迂回しない。
